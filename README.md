# MSMU-SST-CO: Edge-AI-based Selective Subtask Offloading in UAV-Supported MEC

**Version 1.0.1** · Reproducible seed `42` · Version 1.0.1 changes the README only (§5.3a, §12); no data changed
**DOI:** [10.5281/zenodo.22084174](https://doi.org/10.5281/zenodo.22084174)

This repository contains the generation pipeline, datasets, and experiment code for an
**Edge-AI-based selective subtask computation offloading** framework in UAV-supported
multi-server multi-user mobile edge computing (MEC).

The project:

- Generates base task-level MEC offloading scenarios using the MCMF solver from the MSMU-CO
  tool as an offline oracle for optimal task-level offloading decisions.
- Decomposes each user task into *K* = 3 subtasks and derives **oracle selective-offloading
  labels** under the MSMU-CO cost model.
- Augments the environment with **UAV-supported MEC semantics**: UAV versus ground servers,
  3D geometry, elevation, and line-of-sight probability.
- Trains a lightweight **Edge-AI model (MLP)** to predict per-subtask offloading decisions
  from task, channel, and UAV context.
- Benchmarks against naive baselines (all-local, all-MCMF, random) and an **LR-style greedy
  optimization baseline**.

MSMU-SST-CO is the first release in a dataset family. It is extended by
[MSMU-UAV-CO](https://doi.org/10.21227/gzx7-k572), which adds a time horizon and a 100-UAV
swarm.

## 1. Provenance and Originality

**All data in this release is original work, generated by the scripts distributed with it.**

`generate_base_dataset.py` imports two functions — `solve_once` and `range_random` — at
runtime from the MSMU-CO generation tool of Liang et al.
([github.com/qiyu3816/MSMU-CO](https://github.com/qiyu3816/MSMU-CO)), which the user clones
separately (§3.1), and calls them with the parameters specified in that script. All
remaining logic is original to this project, including the bipartite connectivity
construction, the cost-model evaluation, the subtask decomposition and oracle labelling, the
UAV overlay, the Edge-AI model, and the baselines.

Specifically:

- **No MSMU-CO data is used or redistributed.** The 800 scenarios here were generated, not
  downloaded. Their regimes — *S* ∈ {3, 5} × *U* ∈ {10, 20} — do not correspond to any
  server/user combination in the published MSMU-CO dataset release.
- **No MSMU-CO code is redistributed.** The two imported functions are loaded at runtime
  from a repository the user clones independently; no upstream source file is included here.
- **The cost model follows the formulation published by Liang et al.** and is cited
  accordingly. It is reimplemented in this project's own code.
- `generate_graph` in `generate_base_dataset.py` mirrors the structure of the upstream
  connectivity generator, with a documented fix: it caps a user's connection count at the
  available server count, which the original does not, and which raises a sampling error at
  *S* = 3. The deviation is noted in the function docstring.

The pipeline is deterministic (`random.seed(42)`, `np.random.seed(42)`), so all outputs
regenerate exactly.

## 2. Project Overview

### 2.1 Problem Setting

A multi-server multi-user MEC system in which each ground user generates a computation task
that may be processed locally or offloaded to one of several edge servers (UAV-borne or
ground). Each task is decomposed into three subtasks — pre-processing, heavy compute, and
post-processing — enabling **selective subtask offloading** rather than all-or-nothing
offload.

The objective minimises a weighted sum of latency and energy per user, subject to server
capacity constraints, using user-specific latency–energy trade-off weights `alpha`.

### 2.2 Pipeline

| Step | Script | Produces |
|---|---|---|
| 1. Base scenario generation | `generate_base_dataset.py` | `data/raw/base_msmu_raw.parquet` |
| 2. Subtask mutation + oracle labels | `build_subtask_dataset.py` | `data/subtask/{train,val,test}_subtask.parquet` |
| 3. UAV augmentation | `build_uav_dataset.py` | `data/uav_subtask/{train,val,test}_uav.parquet` |
| 4. Edge-AI training + evaluation | `train_edge_ai.py` | `models/`, `output/` |
| 5. LR-greedy baseline | `add_lr_greedy.py` | updated `output/` |

## 5. Reproducing the Pipeline

### 5.1 Step 1 — Base scenarios

```bash
python generate_base_dataset.py
```

Generates 200 scenarios in each of four regimes (*S* ∈ {3, 5} × *U* ∈ {10, 20}), for 800
scenarios and 12,000 users total, in long format with one row per (scenario, user) pair.

For each user the table records task data size, required CPU cycles, local CPU frequency,
the latency–energy weight `alpha`, connectivity count, channel gains, and the MCMF-optimal
assignment (`mcmf_assigned_server`, with −1 denoting local execution) together with its
resource-allocation ratio.

Global parameters, constant across servers and attached to every row plus written to
`base_msmu_config.json`:

| Parameter | Value | Meaning |
|---|---|---|
| `F_t` | 3.36 × 10¹⁰ cycles/s | Server CPU capacity |
| `theta` | 2.0 s | **Maximum tolerable delay** |
| `P_t` | 0.3 W | Transmit power |
| `P_I` | 0.15 W | Device power while awaiting remote execution |
| `kappa` | 1 × 10⁻²⁸ | Local-computation energy coefficient |
| `B` | 8 × 10⁷ Hz | Channel bandwidth (80 MHz) |
| `N0` | 7.96159 × 10⁻¹³ | Noise power |
| input size | 2 – 11 Mbit | Truncated normal, μ = 6.5 Mbit, σ = 3 Mbit |
| local CPU freq | 1 – 10 GHz | Truncated normal, μ = 6.4 GHz, σ = 5 GHz |
| cycles per bit | 3 × 10³ | `required_cycles = input_size × 3000` |

> **Note.** `theta` denotes the maximum tolerable delay in seconds, not a path-loss
> exponent. It is used in the feasibility tests `local_sat`, `trans_sat`, and `offload_sat`.

### 5.2 Step 2 — Subtask mutation and oracle labels

```bash
python build_subtask_dataset.py
```

Loads `data/raw/base_msmu_raw.parquet` and splits each user task into *K* = 3 subtasks
(pre, heavy, post) with random weights. Three patterns are evaluated per user under the
MSMU-CO cost model:

- **P1** — all subtasks offloaded to the MCMF anchor server
- **P2** — selective offload (heavy subtasks offloaded, light ones local)
- **P3** — all local

The minimum-cost pattern becomes the **oracle selective-offloading decision**, yielding
labels `exec_location_label` (0 = local, 1 = offload), `exec_is_local`, and
`exec_server_index`. Output is split into train / val / test by `scenario_id`, producing
36,000 subtask rows.

### 5.3 Step 3 — UAV augmentation

```bash
python build_uav_dataset.py
```

For each scenario, designates 1–2 servers as UAVs and the rest as ground servers, samples 3D
positions for all servers (UAVs at altitude, ground at *z* = 0) and positions for all users,
then derives distances, elevation angle, LoS probability, and effective rate to the anchor
server, plus scenario-level context (UAV count, minimum distance to any UAV, coverage
indicators).

### 5.3a Note on the uplink rate model

- **Rate used for the oracle labels and for every reported cost.** For an offloaded subtask the
  uplink rate is *R* = *B* log2(1 + *x*) with *x* = *P*tx *h*² / (*N*0 + *P*tx *h*²), where *h* is
  the user's `best_channel_gain` (`build_subtask_dataset.py`, function `uplink_rate`). This is a
  bounded, single-user form of the expression in the MSMU-CO generator, whose denominator adds
  *P*tx *h*j² over all users connected to the same server. In this release users therefore do not
  interfere with one another on the uplink, and each offloading user may use the full bandwidth
  *B*. Earlier documents call *x* an "SINR"; it is not a signal-to-interference-plus-noise ratio
  in the usual sense.
- **Consequence.** Because *P*tx *h*² is many orders of magnitude larger than *N*0 for every user,
  *x* is close to 1 and *R* is close to *B*. `python check_rates.py` reports, over the 36,000
  subtask rows: *h* from 0.00139501 to 0.999878 (median 0.708637); *R* from 79.999921 to
  80.000000 Mbit/s; no row below 99.9 % of *B*. The channel gain therefore has practically no
  effect on the latency, energy or cost of an offloaded subtask. Offloading decisions are driven
  by the 0.2 s setup delay, the subtask workload, the server share and the user's latency–energy
  weight.
- **UAV-augmentation rate.** The column `assigned_effective_rate` (`build_uav_dataset.py`) uses
  *x* = *P*tx *h*eff / *N*0, a signal-to-noise ratio, also without interference. It is descriptive
  only: it is excluded from the model inputs by the leakage guard (`train_edge_ai.py`,
  `LEAK_COLS`) and is not used in any cost.
- **Where users are coupled.** Users interact through the MCMF server assignment, computed by the
  MSMU-CO generator with its interference-aware rate, and through the sharing of server CPU (the
  MCMF resource ratio, or 1/*U*).
- **Why this model.** The release studies which subtasks are offloaded and where computation is
  placed, so the radio model is kept simple; the bounded form also avoids the very large Shannon
  rates of the high-SNR form. Interference and bandwidth sharing are left to future versions.

### 5.4 Step 4 — Edge-AI training and evaluation

```bash
python train_edge_ai.py
```

Trains an MLP classifier (21 → 256 → 128 → 1, ReLU with dropout) with BCE loss and Adam on
`train_uav.parquet` and `val_uav.parquet`, using task, subtask, global, and UAV-context
features against target `exec_location_label`. The best checkpoint is saved to
`models/subtask_uav_mlp.pt`.

Evaluation on `test_uav.parquet` compares against the oracle, all-local, all-MCMF, and
random baselines, reusing the same cost model to compute per-user latency, energy, and cost;
deadline violation rate (deadline = 1.5 × median oracle latency); and subtask-level
classification metrics (accuracy, precision, recall, F1, AUC).

### 5.5 Step 5 — LR-greedy baseline

```bash
python add_lr_greedy.py
```

Computes, for each user, the cost difference between all-local and all-offload-to-anchor,
sorts users by cost gain, and greedily admits offloading subject to server capacity. Results
are added to `output/` as method `lr_greedy` and the figures are regenerated.

## 7. Adapting This Pipeline

- Substitute a different base generator in `generate_base_dataset.py`.
- Change the subtask structure or cost model in `build_subtask_dataset.py`.
- Alter UAV geometry or the channel model in `build_uav_dataset.py`.
- Replace the MLP in `train_edge_ai.py` with another model class (GNN, transformer, DRL).
- Add baselines alongside `add_lr_greedy.py`.
